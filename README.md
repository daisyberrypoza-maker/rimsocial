# Clipverse

Short-video social app.
- Backend: Node.js 20, Express, Sequelize + MySQL, Redis
- Web and mobile frontend: React + Vite, wrapped for Android with Capacitor

## Repository layout

```
clipverse/
├── backend/            Express API, worker, Sequelize models
├── frontend/           React app (web and Android source)
│   ├── src/            Application code
│   ├── scripts/        mobile-setup.sh
│   ├── capacitor.config.json
│   └── android/        Generated by `npm run mobile:setup` (not in the zip)
└── docker-compose.yml  MySQL and Redis for local development
```

## 1. Local development (web)

```bash
docker compose up -d                 # MySQL and Redis

cd backend
cp .env.example .env                 # set JWT_SECRET and PAYSTACK_SECRET
npm install
npm run dev                          # API on http://localhost:3000

# in another terminal
cd backend && npm run worker         # views, holds, payouts (optional locally)

# in another terminal
cd frontend
npm install
npm run dev                          # http://localhost:5173
```

## 2. Android app

Requirements: Node 18+, JDK 17, Android Studio (Ladybug or newer, with an Android SDK).

**Before the first build**, set the public API address in `frontend/.env.production`:

```
VITE_API_URL=https://api.yourdomain.com
```

The API must be served over HTTPS and must list `https://localhost` in `CORS_ORIGINS`.

Then create the native project once:

```bash
cd frontend
npm run mobile:setup                 # installs, builds, runs `cap add android`, syncs
npm run mobile:open                  # opens android/ in Android Studio
```

The first `mobile:setup` run creates the `android/` folder. Keep it in version control.
Every later change to the React code needs `npm run mobile:sync` before you run or build in Android Studio.

### Release checklist

1. **Application ID.** `appId` in `capacitor.config.json` is `com.clipverse.app`. Confirm it, or use your own domain in reverse order. Google Play does not allow changing it after the first upload.
2. **Icons and splash screen.** Put `icon.png` (1024×1024) and `splash.png` (2732×2732) in `frontend/resources/`, then run `npx @capacitor/assets generate --android`.
3. **Version.** In `android/app/build.gradle`, raise `versionCode` on every upload and set `versionName` (for example `1.0.0`).
4. **Signing.** Create an upload keystore once and keep it safe, outside the project:
   ```bash
   keytool -genkeypair -v -keystore clipverse-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias clipverse
   ```
   Configure it in Android Studio: Build > Generate Signed App Bundle / APK. Never commit the `.jks` file or its passwords.
5. **Build.** Build > Generate Signed App Bundle, choose **Android App Bundle** and the **release** variant. Upload the `.aab` to Play Console.
6. **Coin purchases.** Coins sold inside the Android app must use Google Play Billing. The current build shows a "coming soon" message in place of Paystack checkout, which is the web-only path.

## 3. Production web

`cd frontend && npm run build`, then run the backend on port 3000. It serves the built app at `/`.

## Data that persists on the device

Session, last screen, cached feeds and scroll position, gifts, coin balance, and the upload caption draft are kept in localStorage under `clipverse-app`. Clearing app data resets them.

## Not included yet

- Video transcoding and S3/CDN storage. Uploads are stored on the local disk for now.
- Google Play Billing for coin purchases.
- Paystack transfers for creator payouts (payouts are created as "pending").
- Moderation tools and an admin panel.


## Find, Flip & Fix business workflows

The signed-in Business tab exposes three workflows: **Find** approved opportunities, **Flip** by making/accepting offers, and **Fix** by assigning a professional, posting progress/blocker updates, submitting completion evidence, and requiring both parties to confirm completion.

- Business profiles and opportunity listings start as **pending review**. Public discovery only returns operator-approved opportunities. Review endpoints are protected by `ADMIN_API_KEY` through the `X-Admin-Api-Key` header.
- API routes are under `/v1/business`. The frontend uses the configured `VITE_API_URL`, so the feature works with independently hosted frontend/backend deployments when CORS is configured.
- Money is represented in integer minor units (for example, ₦1,000.00 = `100000` NGN minor units). Do not send decimal currency values to the API.
- **Important:** this workflow currently records offers and completion confirmations only. It does not collect, escrow, verify, refund, or transfer money. Do not describe an accepted offer as a paid transaction. Paystack checkout/webhook/settlement integration and dispute-resolution operations remain a release blocker before real-money deals.
- HTTPS evidence links are optional. A link is not independently verified just because it was submitted. Operator approval is a moderation state, not a guarantee of business performance or investment returns.
- Development uses the existing additive Sequelize table creation when `DB_SYNC=true`. Production uses `DB_SYNC=false`; apply `backend/migrations/019-find-flip-fix.sql` to the configured MySQL database before deploying the new API. The SQL is additive and does not delete existing records.

Operator review API:
- `GET /v1/business/admin/opportunities?status=pending`
- `PATCH /v1/business/admin/opportunities/:id/review` with `{ "decision": "approve" }` or `{ "decision": "reject", "note": "..." }`
- `GET /v1/business/admin/profiles?status=pending`
- `PATCH /v1/business/admin/profiles/:id/review` with `{ "decision": "approve" }` or `{ "decision": "reject" }`

## Creator monetization and database bootstrap

- Copy `backend/.env.example` to `backend/.env` and set a strong random `JWT_SECRET`, the real MySQL username/password, and a Paystack **test** secret while developing.
- `DB_USER` is the MySQL login name (for example `clipverse_app`), not `localhost`. `DB_HOST` is the host. `DB_PASS` is the MySQL password. Do not put a file URL in either password variable.
- At startup the backend creates the configured database if missing, then Sequelize creates missing tables and indexes. The MySQL account must have permission to create the database. For production, use a dedicated least-privilege account and reviewed migrations rather than `sync()` schema changes.
- Creator Studio is available at `/creator`. It shows held and available earnings, gift/post counts, payout history, creator activation and a basic creator-match invitation flow. Withdrawal requests are blocked until a verified payout profile/recipient exists; do not bypass this guard or treat a client-side payment success as proof of payment.
- Paystack secret keys must exist only in `backend/.env`; never use `VITE_*` for a secret. If any real key was previously shared, rotate it in the provider dashboard. Use HTTPS, rate limiting, provider-side webhook verification, reconciliation and manual payout review before launch.
- LIVE matches use authenticated WebRTC signaling for creator-to-creator video. This is not public-audience broadcasting; configure `TURN_URLS` and `TURN_SECRET` (or fixed TURN credentials) for relay support. A TURN server must be provisioned separately.
- Battle scores are reconciled server-side only from gifts explicitly attributed to that exact match through `liveMatchId`. Ordinary feed gifts and historical gifts without match attribution do not count toward battle scores. The current live-room UI still needs a gift control that submits `liveMatchId` to make this end-to-end.
- WhatsApp sharing uses a user-initiated `wa.me` share link. Automatic WhatsApp messaging requires an approved WhatsApp Business Platform integration and user opt-in.


### Operator payout processing

Pending creator withdrawals can be reviewed through `GET /v1/admin/payouts` with the `x-admin-api-key` header, then submitted to Paystack through `POST /v1/admin/payouts/:id/transfer`. If Paystack returns `requiresOtp: true`, the trusted operator can submit the one-time code to `POST /v1/admin/payouts/:id/otp`. Keep `ADMIN_API_KEY` private and use it only from a trusted server-side operator tool, never from the frontend. Signed Paystack transfer webhooks settle successful payouts or return failed amounts to the creator wallet. Configure the Paystack webhook URL as `/v1/webhooks/paystack`, and test transfer events using Paystack test mode before production.

## Cloudinary media cleanup and retries

Before deploying the media cleanup queue with `DB_SYNC=false`, apply `backend/migrations/020-media-cleanup-jobs.sql` to the production MySQL database.

- Failed post/story uploads are immediately scheduled for deletion if the database write fails.
- Replaced avatars are queued for deletion only when no current post/story/avatar references the asset.
- Removing a post hides it immediately; if Cloudinary is unavailable, cleanup is persisted and retried with backoff.
- Expired stories are removed from the database only after their asset is deleted, found to be shared by other live content, or durably queued for retry.
- The server processes due cleanup jobs and retries removed media approximately every ten minutes. If Cloudinary credentials or the cleanup table are missing, the server logs the failure and retains a reference where possible instead of pretending cleanup succeeded.
- The cleanup worker checks current live content before deleting an asset, so reused/shared media is not removed while another post, story, or avatar still references it.

Do not manually delete `media_cleanup_jobs` records while their status is `pending`; they are the durable retry queue.


## LIVE match gift attribution migration

Before deploying the LIVE battle gift-attribution changes with `DB_SYNC=false`, apply `backend/migrations/022-live-match-gift-attribution.sql` to the production MySQL database. This adds a nullable match reference to gift transactions; existing financial records are preserved and existing gifts without a match reference are not retroactively counted in battle scores.


## Public LIVE broadcasting

RimSocial public LIVE uses LiveKit as the media SFU. The host publishes camera/microphone tracks; audience members join as subscribe-only participants. Audience chat is stored in MySQL and rate-limited per user.

1. Configure `LIVEKIT_URL`, `LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` in the backend environment. Never expose the API secret to the frontend.
2. Apply `backend/migrations/024-public-live-broadcasts.sql` before production deployment. Development databases with `DB_SYNC=true` create the Sequelize models automatically.
3. Build and deploy the backend and frontend together. The web client loads the LiveKit browser SDK at runtime; the browser/device must be able to reach the configured LiveKit URL.
4. Verify camera/microphone permissions, viewer playback, reconnect behavior, chat moderation/rate limits, and ending broadcasts on web and physical Android devices during the final project test pass.
